## Product loop: prompt, object canvas, durable `.op`

OpenPencil is a Rust-based vector design product whose ordinary path is:

`brief or imported interface → editable vector document → direct manipulation and/or agent edits → saved .op → image, code, Git or collaboration handoff`

The user can describe an interface in chat, watch a design appear on the canvas, select existing elements for follow-up changes, and continue editing through normal vector-editor controls. Complex prompts can be decomposed into spatial subtasks and generated by multiple workers. The same document can also be opened or driven through the native desktop app, browser editor, VS Code custom editor, `op` CLI or MCP.

Inputs include Figma `.fig`, HTML and captured web snapshots. Outputs include the canonical `.op` document, raster/vector exports and generated React, HTML, Vue, Svelte, Flutter, SwiftUI, Jetpack Compose or React Native code. These import/export paths surround the design document; none replaces it as the live editor's source of truth.

The surfaces do not all expose equal authority:

- the native and browser applications are full editors backed by the Rust core;
- the VS Code extension opens `.op` in a daemon-backed custom editor only after workspace trust, otherwise it stays read-only;
- `op start` can launch a live native editor, a browser editor or a windowless file-backed MCP server;
- the published vanilla/React/Vue web SDK family is deliberately **read-only**;
- the browser host supports built-in API-key agents, while CLI and ACP agents remain native-only at the pinned revision.

That split matters when evaluating a demo: rendering a `.op` file in the embeddable SDK does not establish that an embedding application can edit it, and using the CLI/MCP server does not establish that the public web surface exposes the same external-agent adapters.

## The `.op` file is the authority, not a generated preview

### Canonical document

The durable artifact is a JSON `.op` document represented by `jian_ops_schema::PenDocument`. It owns the document version and name, root children or pages, themes and variables. Image payloads travel through the repository's companion image-table machinery rather than appearing as a visible `PenDocument` field. The document can also carry interaction/application fields such as routes, state, lifecycle and logic modules, plus `design_md` and a code-to-design conversion ledger.

The node graph is a tagged `PenNode` union. At the pinned schema revision it includes frames/groups, geometric primitives, paths, text/images/icons, references and interactive control-shaped nodes such as inputs, switches, sliders, tabs and progress indicators. Nodes and pages carry explicit string IDs.

`op_editor_core::EditorState.doc` is that same `PenDocument`; there is no second editable scene model that must later be reconciled with the saved file. Selection, active tool, viewport, undo stacks, chat/codegen state and editor chrome live around it as transient state. Variables and themes that affect the design itself remain inside the document.

A whole-document replacement deliberately clears document-derived drafts, selection and history while preserving unrelated editor chrome/settings/chat/tool/viewport state. The editor tracks document generation, monotonic revision and saved revision separately so an old save completion or an undo cannot incorrectly declare a newer document clean.

### Mutation spine

All normal mutation surfaces converge on typed `EditorCommand` values. UI actions, in-process AI tools and MCP write tools therefore do not each invent their own document-write implementation.

`EditorCommand::Batch` is atomic only for commands covered by the editor snapshot contract: the editor snapshots before applying, rejects unsupported transient commands, and restores the whole covered state if any subcommand fails. Clipboard, viewport, tool-switch and history commands are intentionally excluded from this transactional batch.

Collaboration capture adds a second boundary around a local edit: an `EditTransaction` records exact before/after `PenDocument` values and can accept or roll back the local mutation before it becomes a collaboration transaction. Local, remote-commit, replay and snapshot origins are explicit so a remotely installed document is not accidentally re-submitted as a fresh local edit.

## One document, two editor hosts, one read-only SDK

The current implementation is a Rust workspace. The earlier TypeScript/Electron product was retired before v0.8.0; current `apps/*` editor code is not the runtime architecture.

The central projection is:

`PenDocument → resolved DocPayload → paint-only LayoutScene → native Skia or CanvasKit/WebGL canvas`

`op-pen-loader` resolves component references, variables/tokens, text measurement and layout before shaping a paint scene. Layout runs once through the shared layout path; the resulting scene carries resolved bounds and paint data rather than a copy of editor state. The desktop host renders it through the native Skia/Jian stack; the browser host uses CanvasKit/WebGL. The public web viewer packages reuse the wasm renderer but omit editing.

The native host treats `EditorState` as canonical and lazily rebuilds the scene only when document/theme/page/font inputs change. Canvas paint and canvas hit testing both read the same refreshed `LayoutScene`, reducing the chance that a user clicks geometry different from what was painted. Inactive pages can retain metadata while omitting their render children, so a large multipage document need not render every page into the active scene.

### Target identity is document identity

When a schema node becomes a scene node, its existing document ID is copied into the `LayoutScene`. Selection and hit-test results can therefore return directly to the corresponding `.op` node and feed a command addressed by that ID.

This is **canvas-node ↔ design-document-node identity**. It is not DOM-to-React-source mapping and it does not require an injected runtime selector. A generated HTML element or exported React component does not automatically retain a live pointer back to its originating `.op` node, and an imported source path does not become a general reverse source map.

## Agents cross the command boundary; they do not own a parallel canvas

### Built-in design loop

The built-in design loop advertises a narrow 15-tool surface assembled from the same schemas used by MCP. It contains document/canvas reads, variables/design-system operations, `batch_design`, screenshot/export, tool search and `spawn_agents`; it does not register the optional generic Bash/file-edit tool pack from `agent-rs`.

The loop executes a write by rebuilding a tool snapshot against the latest `EditorState`, dispatching it to an `EditorCommand`, applying that command on the host/UI boundary and returning the result to the model. After `batch_design`, deterministic diagnostics can report layout, contrast, icon, empty-shell, navigation and variable problems into the next model turn. A final structural backstop runs only for the gated design-generation loop, not ordinary chat.

The main orchestration path has four product-specific stages:

1. plan the requested interface, retrying an invalid/transient plan twice before a heuristic fallback;
2. create or reuse canvas scaffolding;
3. run section/screen subtasks, sequentially or concurrently;
4. clean up and validate the resulting document.

Concurrent workers do not share a mutable document. Each receives an isolated `BufferDocSink` over the same pre-run snapshot. Successful command buffers are replayed into the real sink in deterministic order; screen-group replay uses atomic batches. The explicit `spawn_agents` tool uses the same subtask runner and isolation model but fans out independent model-supplied targets and replays them in specification order.

Subagents generate a constrained batch-design program rather than arbitrary Rust or application source. The current protocol uses sandboxed JavaScript to call insertion primitives such as `I(parent, node)` (and kit insertion where exposed), then turns the recorded program into editor commands. At the pinned MCP schema, a `batch_design` script is limited to 256 KiB of source, 4,096 inserts, two seconds, 64 MiB of runtime memory and 8 MiB of recorded output. If any transactional operation fails, the document remains unchanged and the caller must resend a corrected batch.

Concurrency is therefore real at the LLM/subtask layer but convergence is command replay, not CRDT-style simultaneous mutation. Overlapping or stale assumptions can still make a later replay reject or produce a design-level conflict; isolation prevents shared-memory races, not semantic disagreement.

### External MCP and CLI

The file-backed stdio server loads the same `EditorState`, converts every successful write tool into an `EditorCommand`, applies it and atomically serializes the resulting `PenDocument` back to the target `.op` file. The live editor and web daemon expose related HTTP/live MCP paths. `op` is primarily a launcher and MCP client around those authorities, with direct import helpers for Figma/HTML/snapshots.

At the pinned revision, repository tests pin **123 static MCP schemas** plus **37 document-derived element insertion tools** from the built-in kits. That is a revision-specific catalogue count, not a timeless product claim.

The authority boundary depends on deployment:

- local and managed MCP use the unrestricted profile and can expose tools that touch local files, outbound network, process-global state, host diagnostics or host processes;
- the public multi-account profile filters non-shareable host surfaces and enforces explicit `mcp:read` / `mcp:write` scopes at call time;
- the in-product design loop advertises only its 15 selected tools;
- an external Claude/Codex/OpenCode/ACP process retains its own runtime and permission policy outside this document-command boundary.

The presence of structured permissions in the vendored `agent-rs` library does not by itself prove that every OpenPencil provider path uses that permission manager. Conversely, a document-scoped built-in loop does not make an unrestricted local MCP client a document-only authority.

## Design and code meet through explicit, asymmetric conversions

OpenPencil supports both directions, but they are not one lossless continuous roundtrip.

### Code or rendered UI into `.op`

Figma import, HTML import and browser-snapshot capture convert external structures into `PenDocument` nodes. A separate code-to-design flow records `ConversionSpec` entries for tokens, components and screens. Each entry can retain a caller-stable key, source path, source hash, target root ID and source-node-ID → document-node-ID map. Upsert operations use that ledger to preserve or remap IDs across incremental reruns.

This is durable conversion provenance. It can answer whether a known conversion entry is present or orphaned and can make a repeated import idempotent. It does **not** establish that every later manual canvas edit rewrites the original React/Vue/source file, or that an arbitrary imported DOM node can be navigated back to an exact source location.

### `.op` into generated code

`op-codegen` consumes the canonical `PenDocument`. Pure generators cover CSS variables and React, HTML, Vue, Svelte, Flutter, SwiftUI, Compose and React Native targets; a separate optional AI pipeline can plan, chunk and assemble larger output.

Generated source is a downstream artifact. The conversion ledger lives in `.op`, not in a universal two-way AST binding between generated files and the canvas. After independent edits on both sides, another explicit conversion/generation step—and its conflict policy—is required.

## Four histories solve four different failure modes

| History/persistence layer | Unit and mechanism | What it guarantees | What it does not guarantee |
|---|---|---|---|
| Current `.op` save | canonical document snapshot, serialized on a worker and committed with a unique sibling temp + atomic replacement | a completed older snapshot cannot rename over a newer queued save; success is acknowledged only if document epoch, generation and revision still match | no project-wide transaction across generated code/assets; a successful disk write for an older revision does not mark newer edits clean |
| Editor undo/redo | up to 100 structurally shared snapshots of the canonical document plus selection/page/component and document-derived transient state | variable, theme, component and node edits restore coherently; revision restoration can naturally recover a saved state | in-memory history is not durable version history and view-only UI state is deliberately excluded |
| Live collaboration | owner-ordered, hash-verified `CollabTxn`/`Commit` log with roles, epochs, dedupe, catch-up/snapshot recovery and selective undo | viewers cannot write; guests reconstruct confirmed + pending state; undo becomes an explicit compensating commit where possible | the transport-free open core alone is not a production session; the private production ticket issuer/provider and real two-machine release validation remain separate requirements |
| Git | in-process libgit2 over the whole repository: status, stage, commit, restore, branches, history, remotes and worktree-isolated merge | `.op` files can participate in ordinary repo history; conflicting `.op` blobs expose three merge stages for structured resolution | Git history is not the same as editor undo or live commit sequence, and unrelated repository files remain ordinary file-level Git content |

For `.op` conflicts, `op-opmerge` parses base/ours/theirs and keys the tree by node ID. It can automatically take a one-sided per-node property change when parent/child order stays compatible. Both-side edits, delete/modify cases, reparenting, child additions/deletions and unsafe structural changes surface as `NodeConflict` records instead of being guessed away. Some conflicts can take the remote properties exactly; structurally inapplicable remote choices fall back to keeping the local structure.

This decomposition is the project's real version model: fast local undo, crash-safe current-file persistence, ordered multi-user convergence and durable repository history are connected through the same document but retain different semantics.

## Evidence boundary

- **Established fact:** v0.8.3 Rust workspace, MIT license, canonical `PenDocument`, typed commands, native/CanvasKit hosts, read-only SDK boundary, built-in design tools, orchestrator concurrency, MCP capability profiles, conversion ledger, codegen targets, atomic save, undo, collaboration protocol and Git merge behavior are pinned to public source.
- **Inference:** OpenPencil is best classified as a document-native AI vector editor because every human/agent/render/version path converges on a serializable vector document rather than on application source or a browser DOM.
- **Established discontinuity:** stable canvas node identity stops at the `.op` document boundary; import provenance and generated code do not form a universal bidirectional source map.
- **Established discontinuity:** the built-in design loop is document-scoped, local MCP can be much broader, and external coding agents keep their own authority model.
- **Established discontinuity:** local undo, current-file save, collaboration commits and Git commits are four different histories; none can be cited as proof of the others.
- **Unknown/unverified here:** packaged-app behavior, production hosted service configuration, real provider quality, two-machine collaboration, export fidelity and cross-host visual parity were not accepted from source tests alone.
- **Not established:** lossless Figma roundtrip, automatic canvas-to-original-source rewriting, project-wide atomic versions, a CRDT for concurrent agent buffers, or editing through the published web SDK.

## Research gaps

- Browser- and desktop-validate prompt → concurrent generation → direct edit → save → reopen → export using release binaries, then inspect the produced `.op` and exported artifacts on disk.
- Run the same `.op` through native Skia, browser CanvasKit and the read-only SDK with local/system fonts, images, effects and multipage state to measure real rendering divergence.
- Exercise code-to-design reruns after independent source and canvas edits; document ID preservation, orphan behavior and the exact conflict policy for modified converted nodes.
- Inspect generated React/Vue/mobile targets as runnable applications, not just emitted strings, and test whether interactions/state/routes in `PenDocument` survive each target.
- Validate a real external-agent MCP session under unrestricted local and scoped online profiles, including denied host-resource tools, atomic batch failure and save recovery.
- Perform authenticated two-machine collaboration across reconnect, catch-up, selective undo, conflicting edits, owner departure and local save/fork gates; include the production ticket issuer boundary.
- Exercise Git branch merges containing property-only, reorder, reparent, add/delete and image-table conflicts, then verify both resolved `.op` structure and rendered output.
- Audit provider-specific CLI/ACP permission prompts and cancellation/resume behavior independently from the built-in 15-tool loop.
