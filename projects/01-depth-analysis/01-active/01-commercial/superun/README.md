# Superun

Superun defines design as a decision that precedes implementation. Its ordinary flow is staged — Idea, Preview, Build, Launch — and the pivotal act of design happens early: an initial prompt is refined through questions into an editable idea definition, and only then does the product branch into **four design directions** the user chooses among before anything is built ([getting started](https://docs.superun.ai/superun/introduction/getting-started), [idea refinement](https://docs.superun.ai/superun/features/prompt-question)). The site designer, in Superun's telling, is not the generator of screen pixels but the selector of a direction against a managed full-stack project.

How it implements that is a hosted project whose UI, data model, backend integrations and publication settings are managed together — the canonical artifact is the whole stack, not a screenshot. After a branch is chosen, the user works in a live full-page preview where elements can be edited directly or by language, and feature selection provisions UI, code paths and backend services through Superun Cloud and integrations like Supabase and Stripe ([FAQ](https://docs.superun.ai/superun/introduction/faq)). The distinction between prototype and product is explicit and enforced: the first stages validate UI and workflow with fake data, while development connects real behaviors — a visual preview is never misreported as working software.

The implementation's concurrency model is telling: manual edits are incrementally saved, and generation or branching is blocked during a manual-edit session ([changelog](https://docs.superun.ai/superun/changelog)). That is evidence of a single-writer edit surface but no public proof of multi-user conflict resolution, migration of the canonical intermediate representation, or rollback guarantees. Design here is a deliberately ordered divergence — four branches, one chosen direction, then a whole project — with the design decision held apart from the implementation that follows it.
