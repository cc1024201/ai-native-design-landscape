# Cursor Design Mode and Canvases

Cursor answers "what is design" with two different authorities that happen to wear the same Design Mode label. In Browser Design Mode, the design is whatever a running application renders and the user points at; in Canvas Design Mode, the design is a separate, agent-authored interactive artifact. The two look alike — select an element, speak or draw an intent — but they do not own the same object, and Cursor's architecture is precisely that they do not.

Browser Design Mode treats design as a **target-return aid for existing code**, not a document. Clicking an element compresses the visible runtime into a small, string-based packet: six fields carrying a component label, a CSS-like structural path (misnamed `xpath`), text excerpt, serialized attributes/geometry/style, optional component props, plus a screenshot and any frozen annotation. The inspected build's identity is session-local by design — a WeakMap id and off-DOM tracking that deliberately avoids the foreign attributes which broke React's Fast Refresh. None of it carries a file path, line, or source-map location. The protocol still asks Agent to *find* the authored code; target return stops before source identity, which is why HMR, class churn, portals and repeated list components all invalidate it. The running app stays the observation surface, the repository stays the authority, and any visual edit survives only once Agent re-materializes it as a file change and hot reload proves it. [Design Mode docs](https://cursor.com/docs/agent/design-mode) · [Browser docs](https://cursor.com/docs/agent/tools/browser) · [visual-editor announcement](https://cursor.com/blog/browser-visual-editor)

Canvases give Cursor a second, genuinely durable design object: managed React/TypeScript source that Agent authors, saved as `.canvas.tsx` with an optional `.canvas.data.json` state sidecar via `useCanvasState`, reopened without rerunning the original task and rerun for fresh data. Canvas host buttons are explicitly fire-and-forget — they open a file or start a prompt with no completion receipt — and sharing uploads a read-only live snapshot, not a collaborative checkout. The decisive boundary is that a Canvas associated with a repository is **not** inside that repository: it lives under the user-level `.cursor/projects` area, so its lifecycle and Git are separate. The two loops share a visual gesture and Agent orchestration but not one source of truth — eight independent persistence clocks run from application files and Agent worktrees to preview DOM, target packets, Canvas source and shared snapshots, with no transaction that restores them together. [Canvases docs](https://cursor.com/docs/agent/tools/canvas) · [Shared Canvases](https://cursor.com/changelog/shared-canvases) · [Canvas Design Mode](https://cursor.com/changelog/canvas-improvements)

The core is closed; the shipped 3.13.25 distribution is inspectable but pinned to one compiled build, and the public `cursor/cursor` repo is only an issue/download shell. What makes Cursor distinctive is that its "visual editing" is really two non-roundtripping loops, and an evaluation that collapses them into one canvas-to-code story misses the actual artifact model.
