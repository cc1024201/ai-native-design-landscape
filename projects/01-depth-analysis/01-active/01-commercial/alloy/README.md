# Alloy

Alloy refuses to define design as one artifact. It coordinates **three independently durable domains** — a capture, a hosted prototype session, and a GitHub-backed codebase session — each with its own center of authority, history and recovery. "Design" here is whichever working object you are currently mutating, and the tool's honesty is that these domains do not share one artifact, history or recovery operation. [Evidence: Alloy concepts](https://alloy.app/guide/concepts)

The most distinctive mechanism is the capture boundary. The shipped Chrome extension runs a customized SingleFile pipeline that serializes rendered DOM and CSS, extracts resources and computed styles, takes a screenshot, blocks scripts and video, and packages the result for upload — a faithful **screen-and-code grab** that is explicitly a browser archive, not original application source. It does not carry React/Vue source, lockfiles, source maps, component ASTs, repository paths or revisions. High visual fidelity and source identity are different properties. [Evidence: browser extension / SingleFile foundation](https://alloy.app/guide/browser-extension)

From that capture, a hosted prototype generates its own files, preview, chat, components and visual edits — a **second implementation**. Visual editing grounds intent by selecting a rendered element, then either a targeted prompt or CSS-like WYSIWYG controls. History here is destructive by default: restoring an earlier chat point removes later prototype changes irrecoverably, so Duplicate is the documented branch-preservation action. Export to a React ZIP is a one-way fork, not a synchronized binding. [Evidence: visual editing / export code](https://alloy.app/guide/visual-editing)

The codebase-session path lives under a different authority entirely: Git. Alloy boots a real GitHub repository in an isolated cloud workspace, iterates on a Docker Compose file until the preview renders, and ships work through a branch and pull request. The checked-in `.alloy/environment.json` becomes repository-owned boot truth — an unusually explicit Git-authority contract for a closed product, with the GUI locking read-only once the file is canonical. Alloy MCP is a read projection of session context (metadata, chat, files, some diffs) with no published mutation tools, confirming it as a context/handoff plane, not a shared write transaction. [Evidence: cloud agents / MCP](https://alloy.app/guide/integrations/mcp)

The operational consequence: rendered-page archive → generated hosted prototype → optional React fork, or independently Git repo → cloud checkout → Git diff/PR. No operation restores every column together, so acceptance must treat each domain separately and validate each destination independently.
