# Superdesign

Superdesign splits "design" into two halves and refuses to own the second one. The first half — the act of design — is a **hosted, versioned graph of HTML draft nodes**: projects contain branchable draft nodes, each draft carries its own version history, and everything ends in a current HTML head. The second half — turning that design into the real application — is delegated to the **calling coding agent's repository**, which the product edits only after the user approves and the coding agent implements. There is deliberately no canvas-to-source round-trip; the hosted design and the application source are different artifacts joined by a fetch, not a live binding. This is a staged handoff, not one shared document.

The decisive mechanism is the **skill as a curation layer**: it decides what the remote design service gets to see. On a real-codebase route, the `superdesign-skill` (pinned `dc59c1b`) requires six non-empty `.superdesign/init/` files — components, layouts, routes, theme/tokens, page dependency trees, and extractable-component candidates ([INIT.md](https://github.com/superdesigndev/superdesign-skill/blob/dc59c1b1b9661580831f0b6e0eff8e879967d282/skills/superdesign/references/INIT.md)) — before designing. The CLI ([@superdesign/cli@0.10.0](https://registry.npmjs.org/@superdesign/cli/0.10.0)) reads every `--context-file` as UTF-8, merges one-based ranges, trims around 900 lines to dodge a server `400`, and uploads an array of `{ filename, content }` to an async job polled through `GET /external/jobs/:id`. The resulting arc is deliberately lossy: real application → agent-authored analysis → selected snippets → generated HTML draft, with no public screenshot-diff or source-map acceptance between the ends. Task routing is part of fidelity — reproduce an existing rendered target first and branch variants after, skip reproduction for genuinely new pages in an existing app, and author complete HTML directly if the caller's model designs.

The hosted artifact then behaves like version control for drafts, not for apps. `iterate --mode branch` creates sibling design nodes; `--mode replace` edits one node in place; `revert --to-version <n>` snapshots the current head first so the revert itself is reversible; `get-design` returns the current head plus the full version timeline ([SUPERDESIGN.md](https://github.com/superdesigndev/superdesign-skill/blob/dc59c1b1b9661580831f0b6e0eff8e879967d282/skills/superdesign/references/SUPERDESIGN.md)). Branches preserve alternative design identities; versions preserve the history of one identity — and the skill treats conflating the two as a genuine failure mode. DraftComponents are hosted Petite-Vue templates with bounded props, explicitly not the application's React components, and the import contract is a single-screen, unclassed-body HTML document.

The present product is a sharp departure from the historical 2025 VS Code extension, which used the local HTML/SVG file in `.superdesign/design_iterations/` as its durable artifact and its file path as the canvas-to-source bridge ([legacy `49e2b9d`](https://github.com/superdesigndev/superdesign/tree/49e2b9dd9615c6dae936b326b1ddb85d4f1d6f19)). Today the durable object moved to the server's draft graph, and the final framework implementation is assigned to the coding agent rather than to a canvas. What stays constant is the discipline: design is reviewed where you can branch and revert, and code is written where you actually ship.
