# Framer AI

Framer AI's definition of design is the strongest kind a hosted tool can have: generation must land *inside the same hosted project graph a person edits and publishes*, not in an exported code draft. The current [Framer AI page](https://www.framer.com/ai/) and from-scratch workflow say Agent output behaves like ordinary Framer content — text, layout, colors, and spacing remain editable on the canvas — so the working artifact is the hosted project itself, and the MIT [`framer-api` 0.1.29 declarations](https://unpkg.com/framer-api@0.1.29/dist/index.d.ts) reveal that graph's shape: web and design pages, native `FrameNode`/`TextNode`/`SVGNode`/`ComponentNode` trees, code files with their own version ids, CMS collections/items/fields, localization groups, styles, branches, and deployments.

The decisive mechanism folds the "[Building Agents for Framer](https://www.framer.com/blog/building-framer-agents/)" story into one native graph editor: the Agent reads the current project tree, compresses verbose state, uses a compact edit language, and makes many small edits so the canvas streams progress; `framer.agent.applyChanges(dsl, { pagePath })` creates/updates/removes nodes and returns canonical system ids, with measured layout rectangles, a deterministic linter for type/contrast/accessibility, and an on-demand server-side pixel render for geometry that rules cannot judge. Selection stays inside native identity — `selectionNodeIds`, `pagePath`, and ancestors — never a rendered-DOM-to-file mapping, because the source of truth already is the Framer graph.

The guardrail that makes this trustworthy is the promotion stack, and Framer's own docs are unusually explicit about the non-equivalent states: an Agent finishing ≠ canvas changes on a branch ≠ branch applied to `main` ≠ a version deployed to the visitor domain. A branch is an isolated copy of the *entire* project and applying it updates `main` without publishing ([branching](https://www.framer.com/help/articles/how-to-use-branches-in-framer/)); publishing creates an immutable version link and can expose optimization problems ([publishing](https://www.framer.com/help/articles/publishing-your-framer-website/)); with staging, the base domain follows latest while the custom domain stays pinned until Deploy. The Server API is explicitly *not transactional* — failed commands return in `errors` without blocking the rest — so branch isolation contains partial mutations from `main` but does not make a multi-operation edit atomic. Three control paths (in-app Agent, locally inspectable External Agent via `@framer/agent`, and raw Server API) share the graph but differ in streaming, context richness, and safety.
