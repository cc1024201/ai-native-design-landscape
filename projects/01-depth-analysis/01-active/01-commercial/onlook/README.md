# Onlook

Onlook answers "what is design" by refusing a design document entirely: the **application codebase is the design**. There is no Figma-like intermediate object and no staging tree — the Next.js + Tailwind source that runs the app is the artifact being edited, and the durable unit of design is a reversible change written back into JSX/TSX. At the pinned revision `423e2e92`, the project spells its code/runtime-first architecture in order: load code into a web container, execute and serve it, show the live preview in an iframe, index the code, instrument JSX so rendered elements resolve to source identity, reflect visual edits back into code, and give AI chat the same code plus editing tools. The preview, selection overlay, and every visual affordance are projections; the source is the truth.

The decisive mechanism is **source identity as a first-class, injected property**. The parser ([`packages/parser/src/ids.ts`](https://github.com/onlook-dev/onlook/blob/423e2e924366419e418ee049093872d535eea41a/packages/parser/src/ids.ts)) walks the JSX AST and ensures every non-fragment element carries a unique `data-oid`, repairing missing, invalid and duplicate ids and resolving branch conflicts — a durable identifier, not a transient browser selector, because it is written into the AST itself. It is kept distinct from runtime identity: `data-oid` (source), `data-oiid` (instance), `data-odid` (runtime DOM node) and `data-ocname` (component name) are defined separately in [`packages/constants/src/editor.ts`](https://github.com/onlook-dev/onlook/blob/423e2e924366419e418ee049093872d535eea41a/packages/constants/src/editor.ts). That separation lets one source element be told apart from the many instances and DOM nodes it produces, so a click in the iframe can address the actual source element rather than this particular render of it.

Design growth happens through a **typed, reversible action model**, not ad-hoc mutation. [`packages/models/src/actions/action.ts`](https://github.com/onlook-dev/onlook/blob/423e2e924366419e418ee049093872d535eea41a/packages/models/src/actions/action.ts) defines `update-style`, `insert/remove/move-element`, `edit-text`, `group/ungroup`, `write-code` (carrying diffs), and image ops — each targeted by `domId`, `oid` and `branchId`. Undo/redo in [`history/helpers.ts`](https://github.com/onlook-dev/onlook/blob/423e2e924366419e418ee049093872d535eea41a/apps/web/client/src/components/store/editor/history/helpers.ts) inverts exactly these, covering both visual operations and generated code diffs. The act of design is therefore the same whether a human selects an element in the overlay or the AI writes a diff through chat: both produce typed editor history that lands in the codebase, and both fall under the same undo model. Branching participates in the identity layer too — branch ownership is checked when OIDs are generated, so a source identity is bound to the branch it was created in and can survive branch-aware conflict resolution.

The honest boundary is that this mapping is proven for the supported JSX/Tailwind road, not universal: the README lists non-Next.js/non-Tailwind support as unfinished, so visual-to-source mapping holds for the covered path only, and the closed hosted "AI-native designer" successor should not be assumed to inherit these internals. That precision is the point. Onlook is a code editor that happens to feel visual because the DOM is instrumented to point back at code, and the code stays the single source of truth throughout.
