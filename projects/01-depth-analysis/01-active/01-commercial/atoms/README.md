# Atoms

Atoms, heir to MGX, re-scopes "design" from drawing to **running a product through a team of named specialists** — the brand story literally trades "Vibe Coding" for a "Vibe Business Team" ([mgx-is-now-atoms](https://atoms.dev/mgx-is-now-atoms)). The thing being designed is a whole application-plus-business, and the act of design is coordinated delegation: Mike the Team Leader coordinates Emma (PM), Bob (Architect), Alex (Engineer), David (Data/Iris), Sarah (SEO) and Adrian (Ads) — eight advertised specialists in the live product, though help pages still list seven. This is not a claim that eight long-lived processes exist; the routing packet, role memory and arbitration logic are closed, and the open [`FoundationAgents/MetaGPT`](https://github.com/FoundationAgents/MetaGPT) source (pinned `11cdf466`) is only the historical five-role shape, with messages routed through a leader and archives written as Git commits.

The decisive mechanism is that **execution regime is a selectable policy, not a property of every request**. [Mode Switching](https://help.atoms.dev/en/articles/12129385-mode-switching-guide) lets the user choose Engineer (Alex alone, cheap and focused), Team (multiple specialists), Deep Research (Iris-led, producing a sourced report as its own artifact), or **Race Mode** — where one prompt fans out to multiple model/agent-team paths and candidates are generated in parallel for the user to compare ([Race Mode guide](https://help.atoms.dev/en/articles/12129504-race-mode)). The durable operation is *selection*, not parallel generation: the chosen candidate is the only one that continues, and losing candidates are discarded to save storage. Race is Max-only and disallowed for Supabase/Stripe-integrated projects, so even its "works for all project sizes" claim is narrowed by stateful exclusions.

After a build, design splits at the **selected rendered element**. Under [App Viewer](https://help.atoms.dev/en/articles/12129698-app-viewer) the user clicks a live element and either gets deterministic direct controls (text, typography, spacing — hard-coded without another prompt) or sends the element to Chat for a semantic, code-changing agent build. A Theme of global palette/typography/spacing variables constrains all later generations from the top ([Theme + Visual Editor](https://atoms.dev/blog/introducing-theme-and-visual-editor)). But no public source map ties the clicked pixel to a file, component, or range; the `#`-file reference is similarly asserted, so the product proves rendered-element targeting, not deterministic source return.

Atoms' persistence is genuinely several authorities, or **six ledgers** that no single transaction joins: the conversation/plan, the generated project files, the Race candidate set, live data and services, the preview/build, and delivery/archive. Cloud tilts the balance sharply — [Atoms Cloud](https://help.atoms.dev/en/articles/13036940-atoms-cloud) manages OIDC auth, Postgres, object storage, serverless and Stripe, but to keep database structure aligned with code it **disables history versions and retains only the latest build**, sacrificing recoverable history for schema consistency. Supabase instead hands durable state to an external project, and [GitHub Connect](https://help.atoms.dev/en/articles/13222322-github-connect) is an explicitly manual archive: Atoms is the active workspace, GitHub holds only the milestones the user chooses to push. Remix starts a fresh chat lineage, ZIP captures files but not the hosted system, and a production Publish is an explicit promotion with its own schema/data decision. Because nothing restores all six ledgers as one transaction, a finished agent message, a plan, a version and a loaded preview are four different claims — none alone is a usable release.
