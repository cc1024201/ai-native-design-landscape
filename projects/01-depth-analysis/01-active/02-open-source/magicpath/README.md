# MagicPath

MagicPath answers "what is design" in a way that collapses the old document/code divide: a Design already *is* a runnable Web program. It is a multiplayer canvas whose durable generated artifact is a small React/TypeScript/Tailwind source graph, not a Figma-like node document that later happens to export code. The signature mechanism is that the visual editor targets the rendered DOM of a built revision and tries to reconcile those mutations back into the source files — so editing pixels is editing a program, and the artifact stays runnable at every step. [Quick start](https://www.magicpath.ai/documentation/getting-started/quick-start) · [Visual editing](https://www.magicpath.ai/documentation/features/editing)

## The decisive loop: source-marked DOM returns to a program revision

Every generated element ships with build-time markers — `data-magicpath-path` (a generated file like `HeaderNavBar.tsx`) plus a transform-assigned `data-magicpath-id` and optional `uuid`/`field`/`repeat`/`binding` markers. The injected edit runtime resolves a rendered node to those source keys and records a mutation manifest (before/after geometry, changed property names, structural evidence). Pressing Done emits the manifest with an explicit `base_revision_id`, and the closed server reconciles it into a *new Design revision*. Undo/redo inside a session is DOM recovery; Done is the first durable proof. This is real source-directed targeting — stronger than a screenshot or a raw CSS selector — but bounded: the markers name generated files and transform ids, not authored AST ranges, and the reconciliation compiler itself stays closed. Because reactivity and repeated rendering are real, a style edit to one rendered card can update shared JSX, one literal record, or require an AI edit depending on the program provenance behind that DOM. ## Three authorities, agent-joined, not synchronized

A MagicPath Design and a real repository are separate clocks, joined by an agent rather than continuously synced. Inbound, an external agent reads a repo slice and reconstructs it into a new constrained React mini-app (the repo stays source of truth); outbound, it fetches an exact `selectedRevisionId` and adapts it into the app (the Design is the presentation authority, the app the runtime contract). The public [`code` CLI](https://github.com/MagicPathAI/agent-skills/blob/a1ced96ad9da6c65d9f57d9fef79d944f7192dfe/skills/magicpath/references/cli-reference.md) accepts only `src/App.tsx`, `src/index.css`, and `src/components/generated/**`, hashing baseline files and submitting full replacements against a local `magicpath-code.json`. [Repository contract](https://github.com/MagicPathAI/agent-skills/blob/a1ced96ad9da6c65d9f57d9fef79d944f7192dfe/skills/magicpath/references/working-with-repositories.md) · [Local integration contract](https://github.com/MagicPathAI/agent-skills/blob/a1ced96ad9da6c65d9f57d9fef79d944f7192dfe/skills/magicpath/references/using-magicpath-designs-in-local-code.md)

Every import family — a Figma selection, a website URL, a Chrome capture, a repository slice, a sketch, a screenshot — normalizes into this new React authority rather than preserving a live reverse binding. The source may have been Vue, Svelte or SwiftUI; the canvas result is fresh React reconstruction, so no imported artifact retains a durable AST or node-identity link back to its origin.

The honest boundary: multi-agent briefs produce per-Design revisions that complete independently with no project-wide transaction, and design-system/library edits do not pin a live dependency on already-built Designs. `DESIGN.md` and editable tokens shape later generation; they do not rewind consumers.
