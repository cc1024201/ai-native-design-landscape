# DCC-MCP Unreal

DCC-MCP Unreal answers the question "what is design" the way a DCC bridge must: it refuses to own design at all. The design lives in the Unreal Engine project that a person and their team already hold — levels, actors, Blueprints, materials, cinematics — and this project does not generate, export or persist anything of its own. It is a control plane that gives an external agent capable, capability-gated commands for mutating native engine state. Authority and durability stay with the `.uproject`; the adapter carries no design semantics and no storage. [Pinned repository](https://github.com/dcc-mcp/dcc-mcp-unreal/tree/2f08c19c9c5d6820f2432bf9585a69d0f6c3abea)

## It composes with Epic's server instead of forking it

The implementation's decisive move is provenance. On Unreal 5.8+ the adapter can discover and call Epic's own experimental native MCP Toolsets through a dedicated bridge, preserving Epic's names and schemas; older or Pythonless engines fall back to DCC-MCP's embedded or native-sidecar paths. The sidecar is a real second pathway — a process that can reach the engine even when Python scripting is unavailable — chosen per capability rather than as a single universal answer.

The result is one capability graph with explicit provenance, not a replacement fork of Epic's NoRedist plugin. Coverage is broad by design: actors, assets, Blueprints, levels, materials, cinematics, Niagara, MetaSound, Chaos, gameplay tests and packaging.

Because the bridge never defines what "good" looks like, it survives whatever the team's own design standards are. The engine stays the judge of validity — a command that succeeds against the real scene graph is the only proof that matters — and the adapter's whole value is keeping the agent's reach aligned with what the engine can safely accept. There is no imported taste, no generated design-system, no stored preference; only a well-gated hand on a document the product does not claim.

## Skills make engine constraints legible to the model

Each Skill declares the properties the engine runtime cares about — game-thread affinity, mutability, destructiveness, idempotency and timeouts — so an agent knows what a command will do before issuing it. This is the bridge's real design contribution: translating Unreal's authoritative, frame-bound execution model into a risk vocabulary a language model can reason about, rather than hoping a model infers destructiveness from a tool name. The [cinematics Skill](https://github.com/dcc-mcp/dcc-mcp-unreal/blob/2f08c19c9c5d6820f2432bf9585a69d0f6c3abea/src/dcc_mcp_unreal/skills/unreal-cinematics/SKILL.md) separates queued renders from status and cancellation, and the [build package](https://github.com/dcc-mcp/dcc-mcp-unreal/blob/2f08c19c9c5d6820f2432bf9585a69d0f6c3abea/src/dcc_mcp_unreal/skills/unreal-build-package/scripts/package_project_executable.py) advances a saved project toward delivery. The [actor authoring](https://github.com/dcc-mcp/dcc-mcp-unreal/blob/2f08c19c9c5d6820f2432bf9585a69d0f6c3abea/src/dcc_mcp_unreal/skills/unreal-actors/SKILL.md) and [Blueprint](https://github.com/dcc-mcp/dcc-mcp-unreal/blob/2f08c19c9c5d6820f2432bf9585a69d0f6c3abea/src/dcc_mcp_unreal/skills/unreal-blueprints/SKILL.md) contracts expose the same discipline across graph and logic domains. The [server and catalog](https://github.com/dcc-mcp/dcc-mcp-unreal/blob/2f08c19c9c5d6820f2432bf9585a69d0f6c3abea/src/dcc_mcp_unreal/server.py) routes this single graph — the agent touches the document, never the design itself.
